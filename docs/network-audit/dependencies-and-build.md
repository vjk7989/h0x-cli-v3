## Findings Requiring Attention

1. **Source and release metadata can leave during SEA builds.** A nonempty `SENTRY_AUTH_TOKEN` enables source-map upload to the hardcoded upstream organization `atomic-agent`, project `cli`, independently of runtime analytics/crash-report settings. Maps include original source content by default. The installed plugin also defaults to release creation, finalization, and automatic commit association. See the Sentry section below.
2. **Binary builds execute an unlocked dependency.** `scripts/build-binary.ts:155` constructs `npx --yes postject ...`; invocation is at line 167. `postject` is absent from both package manifests and the installed canonical package tree. A clean build can fetch and execute a registry-selected version outside `package-lock.json`. This is a reproducibility and supply-chain gap, not an observed compromise.
3. **Eval can disclose task content to a hosted judge.** `eval/harness/judge-client.ts:9` defaults to OpenRouter; lines 43-45 select an available key. Lines 76-103 transmit task, reply, and rubric assembled by `eval/harness/build-judge-prompt.ts:28`. An explicit `ATOMIC_AGENT_JUDGE_URL` override still receives the selected key at line 89, including if the destination is local. Endpoint selection and key scoping need to be assessed together.
4. **The download installers still target the upstream repository.** `scripts/install.sh:20` and `scripts/install.ps1:37` default to `AtomicBot-ai/atomic-agent`, despite this working tree's `h0x-cli` package identity and repository at `package.json:2` and line 8. Running those installers without `ATOMIC_AGENT_REPO` would fetch upstream release artifacts, not prove installation of this fork. Header examples also retain `atomicagent.io`.
5. **Install/build/release are not offline even if runtime reporting is disabled.** Five installed lifecycle scripts can resolve/download native tools, CI runs `npm ci`, release performs explicit downloads, Sentry upload, signing-service calls, and GitHub artifact uploads. Runtime consent switches do not control those paths.

## SEA Source Maps and Sentry

The concrete path is `package.json:78` -> `scripts/bundle-sea.ts:51` token gate -> `sentryEsbuildPlugin` configuration at line 108 -> installed bundler-plugin manager -> native Sentry CLI upload.

- **Activation:** any nonempty `process.env.SENTRY_AUTH_TOKEN`, not a CI-only runtime check. The comment says release CI, but a local shell exporting the token also activates it. Release CI supplies this variable at `.github/workflows/release.yml:81`. Runtime privacy settings are not consulted.

Org/project are explicitly passed, so those two environment overrides do not replace the hardcoded values. Auth is provided to the Sentry CLI; its native API routing and server-provided chunk-upload URLs were not observed.
- **Source disclosure:** `sourcemap: "external"` at `scripts/bundle-sea.ts:66` selects a separate file, not stripped source content. There is no `sourcesContent: false`. Installed esbuild's option adapter only supplies `--sources-content` when configured (`node_modules/esbuild/lib/main.js:308`, line 341). The installed platform executable's embedded help says `--sources-content=false` omits `sourcesContent`; this string was read as bytes, not executed. Therefore expect original source text for bundled input files, including dependency input source, in addition to names/mappings. No SEA build was run to measure the generated map.
- **What the plugin uploads:** with no `sourcemaps.assets`, it uses detected build artifacts (`node_modules/@sentry/bundler-plugins/build/esm/core/build-plugin-manager.js:398`), prepares JS/MJS/CJS and adjacent maps, then uploads the temporary directory at line 458. Source-map preparation parses the whole map, adds debug IDs, rewrites only `sources`, and serializes the map unchanged otherwise (`node_modules/@sentry/bundler-plugins/build/esm/core/debug-id-upload.js:119`, line 140, line 143). It does **not** remove `sourcesContent`. Paths/debug IDs, bundled code, embedded literals, and package version can leave; this is not a blanket upload of unrelated workspace files or `.env` files.
- **Additional release data:** create/finalize default true (`options-mapping.js:21`); omitted `setCommits` becomes `{ auto: true, ignoreEmpty: true, ignoreMissing: true }` at line 52. The manager calls release creation at `build-plugin-manager.js:267`, commit association at line 288, finalization at line 306. Expect Git/release association metadata to be eligible for transmission; the exact native CLI commit payload and whether it succeeds depend on local Git context and token permissions.
- **Telemetry:** `telemetry: false` is explicit at `scripts/bundle-sea.ts:113`. The installed telemetry gate immediately returns false (`node_modules/@sentry/bundler-plugins/build/esm/core/sentry/telemetry.js:83`). This suppresses plugin diagnostic telemetry, **not** artifact/release operations.
- **Deletion and distribution:** `filesToDeleteAfterUpload` at `scripts/bundle-sea.ts:118` requests local `.map` deletion; it does not retract uploaded content. Without a token the plugin is not constructed, so the external map can remain locally. `scripts/package-bundle.ts:222` stages selected runtime assets and never copies `dist-sea/*.map`. Ordinary npm packaging is different: `package.json:19` includes `dist/**`; `tsconfig.json:10` enables declaration maps and line 11 JS source maps. No npm pack/publish was run and no final archive was inspected.
- **Failure reporting is misleading:** the error handler logs and continues (`scripts/bundle-sea.ts:123`), but line 153 chooses an "uploaded sourcemap" success message solely from token presence. A successful build exit or that message is not evidence of successful upload/deletion.
